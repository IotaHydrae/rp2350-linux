# S3-01 · 内核裸串口 PL011 诊断打印（earlycon 之前怎么看日志）

> 场景：内核第一条指令就触发异常（AMO 墙，mcause=7），**早于任何 printk / earlycon**，
> 真板完全静默。这时既不能靠内核日志，也不能完全靠调试器（OpenOCD halt/step 会弄脏
> `mscratch`，产生假象）。解决办法：**在内核 trap 路径里直接操作 PL011 寄存器打印**——
> 不经过任何驱动、不经过 printk，像裸机程序一样往串口写字符。
>
> 本文记录这段临时诊断代码是怎么写出来的、为什么能工作、日志怎么解读、什么时候删。

## 1. 为什么需要"裸串口打印"

S3-00 的结论：内核第一条原子操作（`start_kernel → boot_cpu_init → set_cpu_online → amoor.w`）
在 PSRAM 上触发 Store/AMO fault，进入 `die()` → panic。这个故障点在：

- earlycon 注册之前（`setup_arch` 还没跑完）；
- 更别说 console 驱动；
- 而 printk 本身（`set_cpu_online` 用的 `cpumask_set_cpu` 内部有原子位操作）也依赖原子操作，
  被同一个墙挡住。

所以"让内核自己说话"只有一条路：**在最底层的异常入口，绕过内核所有打印设施，
直接读写 UART 硬件寄存器**。这本质上就是我们在 S1 裸机假镜像里做过的 UART 输出，
只是这次跑在内核上下文里。

## 2. PL011 最小知识（够打印就行）

RP2350 的 UART0 是 ARM PrimeCell PL011（r1p5），基地址（datasheet `UART0_BASE`）：

```
UART0 = 0x40070000
UART1 = 0x40078000
```

发送一个字符只需要两个寄存器（都是 32 位寄存器，访问宽度 32 位）：

| 偏移 | 名称 | 作用 |
|---|---|---|
| `0x000` | `UART01x_DR` | 数据寄存器，写低 8 位 = 发送一个字节 |
| `0x018` | `UART01x_FR` | 标志寄存器，bit5 `TXFF` = 发送 FIFO 满 |

发送流程（轮询）：

1. 读 `FR`，若 `TXFF`（bit5，值 `0x20`）为 1，说明 FIFO 满，继续等；
2. `TXFF` 为 0 时，把字符写进 `DR`（低 8 位）；
3. 重复直到字符串结束。

不需要配置波特率/8N1——**bootloader 已经初始化好了 UART0（GP16/17 @ 115200）**，
内核这段诊断只是"借"现成的硬件，不碰 `IBRD/FBRD/LCR_H/CR`。

为什么 noMMU 可以直接访问 `0x40070000`？因为 noMMU 的地址映射是**恒等映射**
（物理地址 = 虚拟地址），`ioremap` 也只是原样返回地址，不需要页表。

## 3. 诊断代码：四件套

全部在 `arch/riscv/kernel/amo-emu.c` 里，标注为 `TEMPORARY DIAGNOSTIC`
（当前未提交，等 earlycon 出字后删除）：

```c
/* ---- TEMPORARY DIAGNOSTIC: raw PL011 poke (UART0 @ 0x40070000) ---- */
#define DIAG_UART	((volatile u32 *)0x40070000)

static void diag_putc(char c)
{
	while (DIAG_UART[0x18 / 4] & 0x20)	/* UART01x_FR & TXFF */
		;
	DIAG_UART[0x00 / 4] = c;		/* UART01x_DR */
}

static void diag_puts(const char *s)
{
	while (*s)
		diag_putc(*s++);
}

static void diag_hex(u32 v)
{
	int i;

	for (i = 28; i >= 0; i -= 4) {
		u32 n = (v >> i) & 0xf;
		diag_putc(n < 10 ? '0' + n : 'a' + n - 10);
	}
}

void amo_emu_diag(unsigned long cause, unsigned long epc)
{
	diag_puts("\r\n[diag] c=");
	diag_hex(cause);
	diag_puts(" epc=");
	diag_hex(epc);
}

static void diag_mscratch(void)
{
	u32 mscratch;

	__asm__ volatile("csrr %0, 0x340" : "=r"(mscratch));
	diag_puts(" mscr=");
	diag_hex(mscratch);
}

static void diag_result(bool ok)
{
	diag_puts(ok ? " ok\r\n" : " no\r\n");
}
/* ---- END TEMPORARY DIAGNOSTIC ---- */
```

几个关键点：

- `DIAG_UART` 是 `volatile u32 *`——防止编译器把寄存器读缓存掉（每次都真正读硬件），
  也对应 earlycon 的 `mmio32`（32 位访问）。
- 轮询 `FR & 0x20`（TXFF），不是 BUSY——TXFF 只管 FIFO 有没有空位，
  写 DR 即入队，足够保证不丢字符。
- `diag_hex` 从高 4 位开始逐 nibble 转小写十六进制，8 个字符，定宽方便对齐日志。
- `diag_puts` 的字符串常量是只读数据，编译进内核后放在 PSRAM，
  此刻 PSRAM 可读（AMO 墙只挡原子写，不挡普通读）。

## 4. 怎么接入异常路径

诊断入口加在 `arch/riscv/kernel/traps.c` 的 `do_trap_error()` 顶部——
所有访问类异常（包括 AMO fault）通往 `die()` 的公共路径：

```c
static void do_trap_error(struct pt_regs *regs, int signo, int code,
	unsigned long addr, const char *str)
{
	amo_emu_diag(regs->cause, regs->epc);   /* 先打一行：cause + epc */
	if (try_amo_emulation(regs))            /* 再试 AMO 模拟 */
		return;
	...
}
```

`try_amo_emulation()` 内部又打了更细的信息（指令字、rs1 地址、funct5、读回旧值、
写后校验），并对照 flash 里的内核副本（`FLASH_KERNEL_BASE + (epc - PSRAM_BASE)`），
用于区分"PSRAM 里指令被写坏了"和"指令本来就不是 AMO"：

```c
if ((insn & 0x7f) != AMO_OPCODE) {
	diag_puts(" r2 i=");
	diag_hex(insn);
	diag_puts(" f2=");
	diag_hex(*(u32 *)(FLASH_KERNEL_BASE + (regs->epc - PSRAM_BASE)));
	...
}
```

`FLASH_KERNEL_BASE = 0x10010000`（分区 0 的 XIP 地址）：内核镜像既在 flash
（XIP 可读）又被拷贝到 PSRAM，两份字节应该一致；若 `i=` 与 `f2=` 不同，
说明 PSRAM 内容已损坏（此前真板就遇到过）。

## 5. 日志长什么样、怎么读

正常上电（不接调试器），UART0 上会看到：

```
[diag] c=00000007 epc=1100ec8c mscr=00000000 ok
[diag] c=00000007 epc=1100ec9e mscr=00000000
[diag] c=00000007 epc=11047c6e mscr=00000000 r2 i=f0000000
[diag] c=00000007 epc=11047c6e mscr=00000000 r2 i=f0000000
...
```

解读：

- `c=00000007`：mcause = 7（Store/AMO 访问 fault）。
- `epc=...`：出事指令地址。`0x1100xxxx` 在 PSRAM 内核正文区。
- `mscr=00000000`：**正常启动时 mscratch 是 0**——异常入口据此判断"内核态"。
  之前 GDB 里看到的 `mscratch=0x1120f3c0` 是 OpenOCD halt/step 弄脏的假象。
- `ok`：这条 AMO 被模拟器成功处理，内核继续跑。
- `r2 i=f0000000`：这不是 AMO（opcode 不是 `0x2f`），是 PSRAM 里指令已被写成
  `0xf0000000`（损坏）→ 模拟器拒绝，走正常 die()，于是反复在同一个 epc 打转。

`i=... a=... f=... old=... chk=...` 那一版更细：指令字、目标地址、funct5、
模拟读到的旧值、写回后读回的值，用来验证模拟器行为。

## 6. 使用注意事项（照抄时的坑）

1. **UART 必须已被 bootloader 初始化**——诊断代码不配置波特率/引脚，
   依赖 S1 里设好的 UART0（GP16/17，115200，8N1）。
2. **访问宽度 32 位**：`volatile u32 *`，与 `mmio32` earlycon 一致；
   DR 寄存器只写低 8 位。
3. **只轮询 TXFF**，不要在异常上下文里做复杂操作；这段代码运行在 M 模式
   trap 上下文（中断已关），打印本身就是自旋等待，安全但慢。
4. **字符串/立即数都放只读段**，此刻能读 PSRAM；不要依赖堆、锁、printk。
5. **这是临时的**：一旦 earlycon 出字，就删掉这段（连同 traps.c 的调用和
   amo-emu.h 的声明），正式提交只留干净的模拟器。
6. 判断"PSRAM 内容损坏 vs 真异常"时，用 flash 里的内核副本对照
   （`FLASH_KERNEL_BASE + (epc - PSRAM_BASE)`）——这个方法以后排查
   "跑到一半指令花掉"的问题还能复用。

## 7. 通用价值

这套"绕过驱动直接 poke UART"的技巧不只属于 AMO 墙：

- 任何**早于 earlycon / console 初始化**的启动死点，都可以在对应路径临时
  插入同样的 `diag_puts`；
- 想在内核之外（bootloader、裸机）打印，这段代码也是最小可用的 PL011 发送例程；
- 若以后要打数字（地址/寄存器值），`diag_hex` 直接复用。

这就是 S1 裸机串口功底在 Linux bring-up 上的直接变现：**硬件不变，
打印的基本功就不变，变的只是调用它的上下文。**
