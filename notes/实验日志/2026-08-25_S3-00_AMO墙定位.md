# 2026-08-25 · S3-00 真板静默：PSRAM AMO 墙定位（GDB）

板子：RP2350A-Minimal · 内核：linux 7.2 riscv32 noMMU M-mode · 工具：OpenOCD(rp2350.cfg USE_CORE rv0) + gdb-multiarch

## 现象

bootloader 打印正常（分区 3MB 拷贝成功），跳转后内核**零输出**。

## 排查过程

1. **QEMU 二分**：把工程 DTB 改造成 QEMU 能跑的形状（memory@0x80000000 + uart8250 earlycon），T1~T7 变体（缺 intc / 缺 timebase / 带 serial 节点）全部能出 earlycon → **DTB 结构与内核路径没问题**，问题在真板侧。
2. **GDB 抓第一现场**：`hbreak *0x11195378`（handle_exception）→ reset 重跑 → 第一次进异常时寄存器还没被处理逻辑弄脏：

```
mcause = 0x7            （Store/AMO fault）
mepc   = 0x1100e94a     （amoor.w.aqrl a4,a3,(a5)）
ra     = 0x1119a216     （调用者，内核代码）
sp     = 0x1120df10     （内核自己的栈，PSRAM——跳转正常）
```

## 结论

- 死因 = **PSRAM 上的 AMO**：`boot_cpu_init()` → `set_cpu_online(0,true)` → `amoor.w` 写 `__cpu_online_mask`（0x2ab558 → 运行时 0x112ab558，PSRAM）。
- `boot_cpu_init` 是 `start_kernel` 第一件事，**比任何 printk 都早** → 完全静默，earlycon 根本来不及注册。
- 机制：Hazard3 把 AMO 实现为排他读-写对，RP2350 排他访问只在 SRAM 支持（手册 3.1.5），PSRAM 上 AMO → Store/AMO Fault。
- 这就是 PLAN 预告的"PSRAM 原子操作墙"，只是它挡在 init_IRQ panic 之前、挡在一切输出之前——比预期更早。

## 下一步

- 正路修法：M 模式 AMO 模拟器（trap 里解码 AMO 指令、单核 + 中断关 = 原子性成立），这是 RP2350 Linux 移植的核心承重工程。
