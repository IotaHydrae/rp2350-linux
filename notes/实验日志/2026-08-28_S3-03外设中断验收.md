# S3-03 Xh3irq 外设中断验收（2026-08-27 ~ 08-28）

> 板子：自研 RP2350A-Minimal；结论：✅ S3-03 验收通过——Xh3irq 中断链通（force 触发 → MEINEXT → MEIP → cpu-intc → chained handler → 测试 handler 输出 '!'）

## 背景与方案

S3-02 建好了 `riscv,cpu-intc`（本地中断，定时器走 MTIP/cause 7）。S3-03 补上外设中断：Xh3irq（Hazard3 自定义中断控制器，非标准 PLIC）把 52 条系统中断线聚合到 MIP.MEIP（cause 11）。写 `drivers/irqchip/irq-rp2350-xh3irq.c`：irq domain（52 线）+ chained handler（循环读 MEINEXT 分发）+ MEIEA mask/unmask。

验收载体（用户拍板）：UART0 RX 中断。踩坑后发现 PL011 RX 中断要 tty open 才使能（无 shell 阶段做不到），改用 **MEIFA force 软件触发 IRQ 33** 验证控制器本身。

## 踩坑时间线

### 1. IRQ 14（USBCTRL）中断风暴

现象：xh3irq 驱动注册后，日志卡在 `timer running at 1000000 Hz`（local_irq_enable 后中断风暴）。GDB 抓 pc 在 `__irq_resolve_mapping`，栈被搅乱；诊断打印确认 **MEINEXT 无限返回 IRQ 14**（`next=0x00000038 irq=14`，每 ~5ms 一条）。

根因：IRQ 14 = USBCTRL_IRQ，复位后中断线一直 assert；且 MEIEA（使能数组）**复位后不是全 0**（诊断读到 bit3/bit14 被置位）。同优先级下 MEINEXT 按编号小优先，14 一直 pending+enabled → chained handler 分发无 handler 的 14 → 没人清源 → 死循环。

修复：① chained handler 分发前检查 `desc->action`，无 handler 的 IRQ 直接 mask（防电平风暴）；② **xh3irq 驱动 init 时清空 MEIEA 全部窗口**（中断控制器启动本来就该全 disable，把复位幽灵位清掉）。

### 2. RISC-V 上 PL011 不 probe（AMBA 总线缺失）

现象：`arm,pl011` 的 DTB 节点没有 `ttyAMA0` 日志——pl011 驱动是 amba_driver，RISC-V 内核没有 AMBA 总线（`CONFIG_ARM_AMBA` 依赖 ARM），`amba_driver_register` 是返回 -EINVAL 的 stub，probe 永远不会发生。

修复（用户方案）：DTB compatible 改成 **`arm,sbsa-uart`**——SBSA 驱动是无条件注册的 platform_driver，不依赖 AMBA 总线，`vendor_sbsa.access_32b=true` 正好满足 RP2350 PL011 的 32 位访问，`current-speed=<115200>` 定波特率，连时钟都不用配。**内核 serial 驱动零改动**。

结果：`ttyAMA0 at MMIO 0x40070000 (irq = 33, ...) is a SBSA` + `console [ttyAMA0] enabled` + bootconsole 禁用后日志继续（S3-04 真 console 的核心现象提前打通）。

### 3. UART RX 中断不触发（tty open 依赖）

现象：往串口发字符不触发中断（测试 handler 不执行）。

根因：PL011 的 RX 中断在 `uart_startup()`（tty 端口被 open）时才注册并使能；console 注册只配置端口、不 open tty。没有 shell open `/dev/ttyAMA0`，RX 中断从未使能。

对策：改用 **MEIFA force**（软件强制 pending）验证 Xh3irq 链本身，不依赖外设状态和时机。真实 UART RX 中断留给 S6（有 shell 后 open tty）。

### 4. 分发调用被误删（最大乌龙）

现象：force 触发后 diag 显示 `irq=33 virq=33`、desc 状态全正常（action 有、disabled=0、masked=0），但 handler 计数器一直为 0。

根因：加"无 handler 防风暴"补丁重写 chained handler 循环时，**`generic_handle_domain_irq()`（真正调用 handler 的那一步）被误删**——函数里只剩查找和位操作，"只查不办"。用户当时就注意到函数里没有调用 handler 的部分，但以为不需要，没点破。

修复：补回 `generic_handle_domain_irq(xh3irq_domain, irq);`。

## 验收现象（最终）

```text
[    0.417611] printk: legacy bootconsole [pl11] disabled
![    0.460947] xh3irq dbg: virq=33 action=(ptrval) disabled=0 masked=0
[    0.461422] xh3irq dbg: MEIEA[0]=0x0000 MEIEA[2]=0x0002 ...
[    0.461784] xh3irq diag: next=0x00000084 irq=33 virq=33
[    0.593021] xh3irq dbg: rx_test_count=2
```

行首的 `!` = 测试 handler 直接写 UART 输出；`rx_test_count=2` = handler 被分发调用。完整链：MEIFA force → MEINEXT 读出 33 → MEIP → cpu-intc → chained handler → generic_handle_domain_irq → handler。

最终干净内核（TEMP 测试代码全删，amba-pl011.c 恢复主线原样）启动正常：`interrupt-controller: 52 external interrupts mapped`、`ttyAMA0 ... is a SBSA`、console 接管、无 IRQ 14 风暴、到 VFS panic 结束。
