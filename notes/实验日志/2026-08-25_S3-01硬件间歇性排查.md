# 2026-08-25 · S3-01 硬件间歇性排查（xip-stress 全通过 + CS 上拉怀疑）

板子：RP2350A-Minimal（PSRAM_CS = GPIO0）· 状态：软件侧已清，硬件间歇性待用户补电阻验证

## 背景：这一天的调试链（简述）

S3-01 目标 = 内核 AMO 模拟器（linux-7.2 `ee2a9d82b`，`CONFIG_RISCV_AMO_EMULATION`）让内核跨过 PSRAM AMO 墙。调试过程中排掉了一连串问题，最终剩下的真板间歇性卡死被指向**硬件**。

## 已确认的事实（按发现顺序）

1. **拷贝损坏**：flash 正确、PSRAM 部分区域错（如内核偏移 0x195644）。修法：bootloader 改 **uncached 窗口写 + 跳转前整段校验**（verify=0）。已验证有效。
2. **WRITABLE_M1**：XIP_CTRL=0x883，SDK 已置位（bit 11=1），不是问题。
3. **mscratch 假象**：GDB 下第一异常 mscratch=0x1120f3c0 → 处理器走"用户路径"崩溃。但**正常启动（无调试器，内核 UART 诊断）显示 mscratch=0、处理器走内核路径、模拟器正常**。结论：OpenOCD halt/step 会弄脏 mscratch（调试器假象）。后续调试以"不接调试器的内核 UART 诊断"为准。
4. **get_cycles64 崩溃更正**：QEMU 里内核崩在 `get_cycles64`（读 `clint_time_val`）。**不是** noMMU GOT 未重定位（noMMU setup_vm 用 PC 相对 `la` 算基址，重定位正常）——而是 DTB 无 clint 节点 → `clint_time_val = NULL` → 解引用空指针。修法 = 加 RP2350 MTIME clint 节点（后续工程，用户原判断正确）。
5. **0xf0000000 异常**：内核模拟器从 PSRAM/flash 读指令字节时间歇拿到 0xf0000000；GDB（调试模块读）同一地址内容正确。缓存开/关都出现过。间歇性。
6. **xip-stress 全通过**：从 PSRAM 执行纯汇编例程（完全复刻内核访问模式），缓存开/关两态 × 全 8MB 写读回（两种 pattern）+ 同地址反复读 10000 次 + flash 读一致性 + 读自己代码区——**全部 0 错**（日志见下）。

## 结论

**硬件数据路径本身可靠**（测试时全 0）。间歇性卡死/损坏（冷启动偶发、复位后正常，bootloader 也偶尔卡死）指向**上电窗口期硬件状态**：

- PSRAM_CS 用的是 **GPIO0（Bank 0）**。Bank 0 pad 复位为**内部下拉**（手册 9.2）→ 上电瞬间 CS1 被断言（低有效=选中 PSRAM）。
- 手册 9.2 明确注明（行 43240）：**"To use a Bank 0 GPIO as a second chip select, you need an external pull-up to ensure the second QSPI device does not power up with its chip select asserted."**
- 用户此前**拆掉了 PSRAM_CS 上的上拉电阻** → PSRAM 在上电窗口期 CS 有效但时钟/数据未定义 → 可能进入坏状态 → 间歇性失败。

**待修**：补 10kΩ 上拉到 3V3（或原阻值）。

## 待办（电阻补好后）

1. xip-stress 复位循环 ×10，确认间歇性消失。
2. bootloader 去掉"缓存禁用"workaround（恢复缓存 ON），重测内核——之前损坏很可能是坏启动假象，缓存禁用可能根本不需要。
3. 内核预期链路：模拟器处理 AMO → earlycon 出字 → `get_cycles64` 崩（clint NULL）→ 加 RP2350 MTIME clint 节点（S3-02）。
4. 删除内核临时 UART 诊断（amo-emu.c/h + traps.c 钩子，当前未提交），正式提交内核改动。
