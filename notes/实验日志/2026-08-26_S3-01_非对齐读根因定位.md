# 2026-08-26 · S3-01 非对齐 32 位读根因定位（0xf0000000 之谜）

> 板子：RP2350A-Minimal（8MB PSRAM CS1=GPIO0，UART0 GP16/17）· 内核：linux 7.2 riscv32 noMMU M-mode + AMO 模拟器（临时诊断版）
> 现象：电阻补好后仍卡死。UART 只有 bootloader 日志 + 反复 `[diag] c=00000007 epc=11047d12 ... r2 i=f0000000 f2=f0000000`；GDB 抓到 PC 停在 `sw a5,60(sp)`（`.Lsave_context` 保存现场中途）。

## 结论（一句话）

**内核代码没问题、flash/PSRAM 内容没问题；问题出在 AMO 模拟器/诊断代码对「2 字节对齐的 32 位指令地址」做了非对齐 32 位读，RP2350 对这种读返回 `0xf0000000`，模拟器永远读不到真实指令。**

## 排查过程

1. **怀疑 flash 内容被写坏**：日志 `i=f0000000 f2=f0000000` 显示 PSRAM 和 flash 同位置都是坏值，而 bootloader verify（flash↔PSRAM 对比）报 0 错误——一度以为烧录环节写坏。
2. **GDB 取证推翻**：调试口读 flash `0x1001ed30` / `0x10057d10`，与内核 Image 文件逐字节一致 → **flash 内容是对的**。
3. **发现地址规律**：所有 `i=f0000000` 的 epc 都是 `≡2 mod 4`（`0x1100ed32`、`0x11047d12`）；成功模拟的那次 epc=`0x1100ece8` 是 4 字节对齐。→ 怀疑非对齐 32 位读。
4. **反汇编证实**：内核开了压缩指令扩展（RVC），32 位指令允许从 16 位边界开始（RISC-V parcel 对齐）。`set_cpu_online` 里 `c.beqz`（2 字节）后面紧跟 `amoor.w.aqrl`（4 字节），AMO 就落在 2 字节对齐地址——**这是合法代码**，CPU 正常执行并报 mcause=7。
5. **根因**：模拟器 `insn = *(u32 *)regs->epc` 在 mepc=2 mod 4 时做非对齐 32 位 load。RP2350 Hazard3 的数据读路径对非对齐 32 位读返回 `0xf0000000`（调试口 DAP 读是对的，所以 GDB 看到真值）。模拟器拿到 0xf0000000 → opcode 不匹配 → 拒绝 → `die()` → 再 fault → 死循环。
6. **「卡在 sw a5,60(sp)」是假象**：异常保存现场每次都要经过 `.Lsave_context`，`sw a5,60(sp)`（0x11195792）是保存序列中一条，GDB halt 恰好抓在那里，实际是 11047d12 故障循环反复进出异常。

## 修复（内核，未提交，测试用）

`arch/riscv/kernel/amo-emu.c` 取指改为**两个 16 位半字拼接**（半字读都是 2 字节对齐，安全）：

```c
u16 lo = *(u16 *)regs->epc;
u16 hi = *(u16 *)(regs->epc + 2);
insn = (u32)lo | ((u32)hi << 16);
if ((insn & 0x3) != 0x3)  /* 16 位压缩指令，绝不可能是 AMO/LR/SC */
	return false;
```

flash 对照读（`f2=`）同样改半字拼接。诊断另加了 `ba=`（mtval 故障地址）和 `sp=`。

## 附带结论

- RVC 下 32 位指令可以在任意 16 位边界 → AMO/LR/SC 的 mepc 也可能是 2 mod 4，模拟器必须按半字取指。
- RP2350 非对齐 32 位 load 返回 `0xf0000000`（不 fault、不拆分），这个硬件行为后续写代码要避开。
- bootloader 的 verify（对齐 u32 对比）是可靠的，之前「flash 写坏」是误判。
